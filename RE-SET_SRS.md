## 1. Introduction

### 1.1 Purpose

This Software Requirements Specification (SRS) defines the functional and non-functional requirements for RE:SET, an AI-powered early wellness intervention system for students. It is intended to guide the design, development, and evaluation of the system for a hackathon submission and any subsequent development. Readers should use this document as the single source of truth for what RE:SET does, how it should behave, and the constraints it must operate within.

### 1.2 Project Scope

RE:SET is a web-based application that helps students notice when their daily routine (sleep, stress, screen time, study load, energy, activity) is beginning to deteriorate, and responds with a small, personalized "recovery" action rather than a generic recommendation or a diagnostic verdict. The system observes short daily check-ins, detects multi-day patterns using a set of cooperating AI agents (Pattern, Risk/Trend, Personalization, Intervention, Reflection, and Safety agents), proposes a short "RESET" micro-intervention, and measures whether the intervention correlated with improved wellbeing the next day. An optional "Campus Mode" aggregates fully anonymized, university-level trends for institutional stakeholders. RE:SET explicitly does not diagnose, treat, or provide clinical mental-health assessment; it is a self-reflection and habit-recovery tool, not a substitute for professional care.

### 1.3 Intended Audience

- Hackathon judges evaluating real-world impact, creativity, technical execution, UX, and accessibility.
- Developers and engineers implementing the frontend, backend, and AI agent pipeline.
- UX/UI designers building the check-in, RESET plan, and insight screens.
- QA/testers validating functional and non-functional requirements.
- University stakeholders evaluating the optional Campus Mode.

### 1.4 Definitions, Acronyms, and Abbreviations

| Term | Definition |
|---|---|
| RESET / RESET Plan | A short (approx. 20-minute), personalized set of micro-actions generated by the Intervention Agent in response to a detected negative wellness pattern. |
| Wellness Signal | A single tracked data point from a daily check-in (e.g. sleep hours, stress level, screen time, mood, energy). |
| Pattern Agent | AI agent that analyzes recent (3-7 day) wellness signals to detect trends. |
| Risk/Trend Agent | AI agent that classifies the user's current state as Stable, Needs Attention, or Recovery Needed. |
| Personalization Agent | AI agent that selects an intervention type based on the user's specific pattern and history. |
| Intervention Agent | AI agent that generates the concrete RESET plan shown to the user. |
| Reflection Agent | AI agent that compares outcomes after a RESET plan is completed and surfaces what seemed to help. |
| Safety Agent | A separate, narrowly scoped classifier that screens check-in text for signs of acute crisis and routes to a safety flow instead of the normal AI pipeline. |
| Campus Mode | An institutional view showing anonymized, aggregated wellness trends across a student population; contains no individually identifiable data. |
| FR / NFR | Functional Requirement / Non-Functional Requirement. |
| RPN | Risk Priority Number (Severity x Occurrence x Detection), used in the FMEA risk matrix. |

## 2. Overall Description

### 2.1 Product Perspective

RE:SET is a standalone, self-contained web application. It is not an extension of an existing product, though it may integrate with a university's identity provider (SSO) in later phases for Campus Mode onboarding. It is designed as a new system built specifically to close the loop between (a) detecting a deteriorating daily routine, (b) generating a personalized micro-intervention, and (c) measuring whether that intervention correlated with improvement — a loop that differentiates it from existing mood-tracker and generic wellness-chatbot products.

### 2.2 User Roles and Characteristics

| Role | Description | Key Permissions |
|---|---|---|
| Student (Primary User) | A university student who performs daily check-ins and receives personalized RESET plans. | Create/view own check-ins; view own patterns, RESET plans, and weekly insights; manage own privacy settings; export/delete own data. |
| University Admin (Campus Mode) | An authorized staff member (e.g. student wellness office) viewing aggregated, anonymized trends for their institution. | View anonymized aggregate dashboards only; no access to any individual student's check-in data or identity. |
| Guest / Unauthenticated Visitor | A visitor exploring the product before creating an account. | View marketing/landing content and a demo walkthrough only; cannot submit real check-in data. |
| System Administrator | Technical operator responsible for system health, moderation, and safety-flow escalation configuration. | Manage user accounts, monitor system health/logs, configure Safety Agent escalation contacts, no routine access to individual wellness content. |

### 2.3 Operating Environment

- Client: modern evergreen web browsers — Chrome, Edge, Safari, Firefox (last two major versions) — on desktop and mobile viewports.
- Responsive layout supporting mobile (360px+), tablet, and desktop breakpoints, since students are expected to check in primarily from phones.
- Server: Linux-based cloud hosting (containerized), reachable over HTTPS.
- No native OS-level dependency; no required hardware beyond a camera/microphone-free standard device (RE:SET explicitly avoids requesting camera, microphone, or contacts access — see Section 3.10).

### 2.4 Design and Implementation Constraints

- Frontend: Next.js with Tailwind CSS and shadcn/ui components.
- Backend: FastAPI (Python) exposing a REST API.
- Database: PostgreSQL.
- AI orchestration: LangGraph coordinating the Pattern, Risk/Trend, Personalization, Intervention, Reflection, and Safety agents, backed by an LLM accessed via API.
- Analytics: Python (Pandas, scikit-learn) for a transparent, rule-based/statistical trend model; the LLM is used for interpretation, language, and personalization rather than as an opaque predictive "diagnosis" model.
- Must be buildable and demoable within a hackathon timeframe — architecture favors a clear MVP path (Section 3) over exhaustive feature coverage.
- Must avoid clinical/diagnostic claims anywhere in copy, UI, or AI output, per the safety framing in the source brief.

### 2.5 UI Overview

RE:SET uses a calm, low-stimulation visual language appropriate for a wellness product: soft neutral backgrounds, a single accent color for primary actions, generous whitespace, and minimal use of red/alarm colors (reserved only for the Safety flow). Navigation is a simple bottom or side tab bar with three primary destinations: Check-In, Today's RESET, and Insights. All interactive flows support keyboard navigation and screen readers, target WCAG 2.1 AA color contrast, and provide descriptive alt text for icons/illustrations. Per-screen UI requirements are detailed within each System Feature in Section 3.

## 3. System Features

### 3.1 Daily Check-In

A fast (target: under 30 seconds), low-friction daily entry point where the student logs mood, stress, sleep, energy, and a short qualitative descriptor of their day. This is the primary data source feeding all downstream agents.

**UI Requirements**
- Single-screen check-in with large tap targets: mood emoji scale (5-point), stress slider (1-10), sleep hours (numeric/stepper input), energy level (Low/Medium/High), and a "today felt..." multi-choice tag (Overwhelming, Normal, Productive, Relaxing).
- Optional free-text note field, clearly labeled as optional and screened by the Safety Agent (see 3.9).
- Progress indicator showing steps remaining; skip/back navigation between fields.
- Empty state: friendly prompt if no check-in exists yet today. Loading state: brief skeleton while submitting. Error state: inline retry if submission fails, with local draft retained.
- Fully keyboard-navigable; slider and stepper controls have accessible ARIA labels and numeric text equivalents, not color/position alone.

**Functional Requirements (FR)**

| FR-ID | Requirement | Priority |
|---|---|---|
| FR-101 | The system shall allow a student to submit at most one primary check-in per calendar day, with the option to edit it until midnight local time. | High |
| FR-102 | The system shall require mood, stress, sleep hours, and energy fields before a check-in can be submitted; the free-text note and day-tag shall be optional. | High |
| FR-103 | The system shall timestamp and persist each check-in against the authenticated student's account. | High |
| FR-104 | The system shall route any submitted free-text note through the Safety Agent before it is used by any other agent. | High |
| FR-105 | The system shall display a confirmation state immediately after a successful check-in submission. | Medium |

**Backend / Logic Notes**
- Validates ranges server-side (e.g. sleep 0-24h, stress 1-10) independent of client-side constraints.
- Writes to the `daily_checkins` table (see Section 6.1) and triggers the Wellness Engine pipeline asynchronously.
- Free-text note is passed synchronously to the Safety Agent classifier prior to storage in plain form; flagged content follows the Safety Flow (3.9) instead of normal processing.

### 3.2 Pattern Recognition (Pattern Agent)

Analyzes the student's most recent 3-7 days of check-ins to identify directional trends (e.g. "sleep is decreasing while stress and screen time are increasing") without making any medical or diagnostic claim.

**UI Requirements**
- Surfaced primarily through the "AI analysis" loading/result screen shown right after check-in, and within the Weekly Insight screen (3.7).
- Presents trend deltas as simple percentage/directional indicators (e.g. "Sleep down 18%") rather than raw model internals.
- Loading state uses a short, calm animation ("Analyzing your recent pattern...") capped at a few seconds; timeout state falls back to a plain-language summary if the AI call is slow.
- All pattern statements are written in plain, non-clinical language and are screen-reader friendly (no meaning conveyed by color alone).

**Functional Requirements (FR)**

| FR-ID | Requirement | Priority |
|---|---|---|
| FR-201 | The system shall compute rolling trend deltas (e.g. 3-day and 7-day) for sleep, stress, energy, screen time, and activity whenever sufficient check-in history exists. | High |
| FR-202 | The Pattern Agent shall generate a plain-language summary identifying the most significant co-occurring trend(s), not a full statistical dump. | High |
| FR-203 | The system shall require a minimum of 2 prior check-ins before generating a trend summary; otherwise it shall show an "insufficient history" state. | Medium |
| FR-204 | Pattern Agent output shall never include clinical/diagnostic language (e.g. named mental health conditions). | High |

**Backend / Logic Notes**
- Computes deltas server-side using a transparent statistical model (Pandas) over the `wellness_signals` table before invoking the LLM.
- Passes computed deltas (not raw diagnosis prompts) to the LLM solely for natural-language phrasing/personalization.
- Persists the generated pattern summary to the `patterns` table for reuse in Weekly Insight and "What Changed?" (3.8).

### 3.3 Wellness State Classification (Risk/Trend Agent)

Classifies the student's current multi-day state into one of three bands — Stable, Needs Attention, or Recovery Needed — to give a fast, glanceable read on how urgent a recovery action might be.

**UI Requirements**
- A compact status card (green/yellow/red-adjacent, but using accessible non-alarming colors) showing the current band, the top contributing signals, and one "main pattern" line.
- Tapping the card expands to show the underlying deltas (from 3.2) that produced the classification.
- State persists at the top of the Insights and Check-In result screens so it is always visible without extra navigation.

**Functional Requirements (FR)**

| FR-ID | Requirement | Priority |
|---|---|---|
| FR-301 | The system shall classify the student's current state into exactly one of: Stable, Needs Attention, Recovery Needed, based on the magnitude and duration of negative trends. | High |
| FR-302 | The system shall display the 1-2 dominant contributing signals (e.g. "Sleep + late-night phone usage") alongside the classification. | High |
| FR-303 | The system shall re-evaluate the classification after every new check-in. | High |
| FR-304 | The classification label and supporting copy shall explicitly avoid the word "score" as a stand-alone health/diagnostic metric without an explanatory disclaimer (see 3.7 Recovery Readiness). | Medium |

**Backend / Logic Notes**
- Applies a rule-based threshold model over the Pattern Agent's deltas (e.g. combined negative-trend duration and magnitude) to assign the band — kept transparent/explainable rather than a black-box ML classifier, consistent with the hackathon's technical-defensibility goal.
- Writes classification result to the `patterns` table with a timestamp for historical/weekly-trend charting.

### 3.4 Personalized Recommendation Selection (Personalization Agent)

Selects which type of intervention best fits the student's specific contributing pattern (e.g. sleep+screen vs. workload vs. inactivity) rather than issuing the same generic advice to everyone.

**UI Requirements**
- No dedicated screen — this agent's output is consumed directly by the Intervention Agent (3.5) UI; internally it is exposed via an admin/debug view for demo/judging purposes only.

**Functional Requirements (FR)**

| FR-ID | Requirement | Priority |
|---|---|---|
| FR-401 | The system shall map each detected dominant pattern (e.g. sleep+screen, workload+inactivity, high stress+low movement) to a candidate intervention category. | High |
| FR-402 | The system shall factor the student's intervention-completion history (Section 3.6) into future selection, preferring intervention types the student has previously completed and that correlated with improvement. | Medium |
| FR-403 | The system shall avoid repeating the identical intervention two days in a row unless the student explicitly requests it again. | Low |

**Backend / Logic Notes**
- Reads the current classification (3.3) plus the student's `intervention_results` history to score candidate intervention categories.
- Passes the selected category (not the full decision logic) to the Intervention Agent for concrete plan generation.

---

### 3.5 RESET Plan Generation (Intervention Agent)

Generates the core deliverable of the product: a short, concrete, personalized recovery plan ("Today's RESET") consisting of a few small timed actions rather than a long list of generic advice.

**UI Requirements**
- "Today's RESET" screen listing 3-4 short actions, each with an icon, short title, and duration (e.g. "10 min — Walk outside").
- Primary "Start RESET" call-to-action; each action can be checked off individually with a lightweight in-app timer for timed actions.
- Completion state ("RESET COMPLETE") with a short affirming message; empty/first-time state explains what a RESET is before the first one is generated.
- Actions are represented with both icon and text (not icon-only) for accessibility, and the timer includes an audible/visual completion cue.

**Functional Requirements (FR)**

| FR-ID | Requirement | Priority |
|---|---|---|
| FR-501 | The system shall generate a RESET plan of 3-4 discrete actions, each under 30 minutes, based on the Personalization Agent's selected category. | High |
| FR-502 | The system shall allow the student to mark each action, and the overall plan, as complete. | High |
| FR-503 | The system shall timestamp RESET plan generation and completion separately to support the Reflection Agent's before/after comparison. | High |
| FR-504 | The system shall allow a student to skip or regenerate a RESET plan at most once per day without penalty. | Medium |
| FR-505 | The system shall always include a one-line reflection prompt (e.g. "What drained your energy today?") as one of the RESET actions. | Medium |

**Backend / Logic Notes**
- Persists generated plans to the `interventions` table, linked to the triggering pattern/classification record.
- Uses the LLM to phrase concrete, contextual action text from the selected category, constrained by a fixed action-count/duration template so output stays predictable for the UI.
- Completion events write to `intervention_results` for downstream Reflection Agent analysis.

### 3.6 Outcome Reflection (Reflection Agent)

Closes the feedback loop by comparing the student's wellness signals before and after a completed RESET plan, and surfacing whether the intervention appears to have correlated with improvement.

**UI Requirements**
- Shown as a short card the day after a RESET completion (e.g. on the next check-in confirmation): before/after deltas for stress, sleep, mood.
- Plain-language takeaway line (e.g. "Your evening phone-free routine seems to have helped") with a note that this reflects correlation, not certainty.

**Functional Requirements (FR)**

| FR-ID | Requirement | Priority |
|---|---|---|
| FR-601 | The system shall compare the wellness signals from the day of RESET completion against the following day's check-in. | High |
| FR-602 | The system shall generate a plain-language takeaway describing the observed change, explicitly framed as an observation rather than a guarantee. | High |
| FR-603 | The system shall feed the outcome (improved / no change / worsened) back into the Personalization Agent's selection history (FR-402). | Medium |

**Backend / Logic Notes**
- Runs on a scheduled/triggered basis after each new check-in that follows a completed RESET within the prior 48 hours.
- Writes outcome to `intervention_results.outcome` for use in the Personalization Agent and Weekly Insight.

### 3.7 Weekly Insight Dashboard

A weekly rollup view showing wellbeing trend bars, key signal directions, and a synthesized insight sentence, designed to be the most visually compelling screen of the demo.

**UI Requirements**
- Bar/sparkline chart of daily wellbeing across the past 7 days, plus directional indicators for sleep, stress, and screen time.
- A single synthesized insight sentence (e.g. "Your difficult days usually follow nights with less than 6 hours of sleep").
- A "Recovery Readiness" composite indicator (weighted from sleep consistency, stress trend, energy, activity, digital balance) always shown with an explanatory disclaimer that it is not a medical score.
- Responsive chart rendering that degrades gracefully to a simple list view on narrow viewports; chart data is also available via an accessible data table, not chart-only.

**Functional Requirements (FR)**

| FR-ID | Requirement | Priority |
|---|---|---|
| FR-701 | The system shall render a 7-day wellbeing trend visualization once at least 3 check-ins exist in that window. | High |
| FR-702 | The system shall compute a Recovery Readiness composite (Sleep consistency 25%, Stress trend 25%, Energy 20%, Activity 15%, Digital balance 15%) and display it alongside a plain-language disclaimer. | Medium |
| FR-703 | The system shall generate at most one synthesized natural-language insight per week to avoid overwhelming the student. | Medium |
| FR-704 | The system shall provide the same trend data in an accessible tabular format alongside any chart. | Medium |

**Backend / Logic Notes**
- Aggregates `wellness_signals` and `patterns` records over a rolling 7-day window; computes the weighted Recovery Readiness score using the fixed weights above.
- LLM is used only to phrase the single synthesized insight sentence from pre-computed statistics, not to invent the underlying numbers.

### 3.8 "What Changed?" Comparative Analysis

An on-demand, student-initiated feature that compares the current week against the student's own historical baseline and identifies the most likely contributing factor to a felt change in wellbeing — the product's signature "wow" feature.

**UI Requirements**
- A single tappable entry point (e.g. "Why do I feel worse this week?") on the Insights screen.
- Result view listing quantified deltas (e.g. Sleep -1.4h, Late screen time +42%) and a single "most likely contributor" line, followed by a persistent disclaimer: "This is a pattern, not a diagnosis."

**Functional Requirements (FR)**

| FR-ID | Requirement | Priority |
|---|---|---|
| FR-801 | The system shall allow a student to request an on-demand comparison between the current week and their own rolling historical baseline. | High |
| FR-802 | The system shall rank contributing factors by magnitude of deviation from baseline and present the top 1-2 as the "most likely contributor." | High |
| FR-803 | The system shall require a minimum of 2 weeks of history before this feature is available, and shall show an explanatory empty state otherwise. | Medium |
| FR-804 | Every "What Changed?" result shall display the fixed disclaimer "This is a pattern, not a diagnosis." | High |

**Backend / Logic Notes**
- Computes baseline as a trailing multi-week rolling average per signal, then computes current-week deviation per signal server-side before any LLM call.
- LLM phrasing is constrained to the pre-ranked factors only, preventing it from introducing unsupported causal claims.

### 3.9 Safety Agent & Crisis Flow

A narrowly scoped safety layer that screens any free-text input for signs of acute crisis and routes matching content to a dedicated, human-help-oriented flow instead of letting the normal personalization/intervention agents respond freely.

**UI Requirements**
- When triggered, replaces the normal AI response with a calm, non-judgmental screen offering crisis resources and encouraging the student to reach out to a trusted person or professional/crisis line.
- This flow is never optional to skip past the resource information, but does not block the student from continuing to use the rest of the app afterward.
- Visual tone deliberately different (calmer, no gamified elements) from the rest of the product for this screen only.

**Functional Requirements (FR)**

| FR-ID | Requirement | Priority |
|---|---|---|
| FR-901 | The system shall run all free-text student input through the Safety Agent classifier before it reaches any other AI agent. | High |
| FR-902 | If the Safety Agent detects potential indicators of crisis or self-harm risk, the system shall display crisis resources and shall suppress the normal Pattern/Personalization/Intervention pipeline for that input. | High |
| FR-903 | The system shall never present Safety Agent output as a definitive risk assessment or diagnosis; copy shall be reviewed to avoid implying the system can reliably detect suicide risk. | High |
| FR-904 | The system shall log Safety Agent activations (without storing unnecessary raw content beyond what is needed for the flow) for monitoring and continuous improvement, subject to the data-minimization requirements in Section 3.10. | Medium |

**Backend / Logic Notes**
- Implemented as an isolated classification step in the LangGraph pipeline, positioned before Pattern/Personalization/Intervention agents so a flagged input never reaches recommendation-generation logic.
- Scope for the hackathon MVP is deliberately conservative: the classifier's role is to route to human-help resources, not to make an autonomous clinical judgment.

### 3.10 Privacy Dashboard & Data Controls

Gives students visibility into and control over their own wellness data, reflecting the sensitivity of the information the product collects.

**UI Requirements**
- A dedicated "Your data" screen listing what is collected, with toggles/buttons for exporting and deleting all personal data, and a plain statement that data is not sold and that the AI does not diagnose the user.
- Confirmation dialog before any destructive action (data deletion/account deletion).

**Functional Requirements (FR)**

| FR-ID | Requirement | Priority |
|---|---|---|
| FR-1001 | The system shall collect only the minimum data needed to operate (check-in signals, optional free-text notes, account credentials) and shall not request camera, microphone, contacts, or precise location access. | High |
| FR-1002 | The system shall allow a student to export all of their personal data in a machine-readable format (e.g. JSON) on request. | High |
| FR-1003 | The system shall allow a student to permanently delete their account and all associated personal data on request, subject to a confirmation step. | High |
| FR-1004 | The system shall display, in-product, a plain-language statement that user data is not sold to third parties and that the AI does not provide medical diagnosis. | Medium |

**Backend / Logic Notes**
- Export/delete requests are handled as asynchronous jobs that cascade across `daily_checkins`, `wellness_signals`, `patterns`, `interventions`, and `intervention_results` tables for that `user_id`.
- Deletion is a hard delete for personal records; any data already folded into Campus Mode aggregates is not reversible since it is stored only in anonymized, non-attributable form (see 3.12).

Supports the target Pakistani student audience with culturally natural language options across check-in prompts, RESET plans, and insight copy.

**UI Requirements**
- Language switcher accessible from account/settings; persists as a user preference.
- All check-in labels, RESET plan text, and AI-generated insight copy render in the selected language, including right layout handling for Urdu script where applicable.

**Functional Requirements (FR)**

| FR-ID | Requirement | Priority |
|---|---|---|
| FR-1101 | The system shall support English, Urdu, and Roman Urdu as selectable interface languages at launch. | High |
| FR-1102 | The system shall persist a student's language preference across sessions. | Medium |

### 3.12 Campus Mode (Institutional Aggregate Dashboard)

An optional institutional view that shows universities anonymized, aggregated wellness trends across their enrolled student population, without exposing any individual's data — turning RE:SET from a single-student tool into an institution-level early-warning signal.

**UI Requirements**
- A separate authenticated dashboard for University Admin users showing aggregate metrics (e.g. overall wellbeing %, sleep concern %, academic stress %, social isolation %) and trend lines over the term.
- No student names, IDs, or individually attributable records appear anywhere in this view.

**Functional Requirements (FR)**

| FR-ID | Requirement | Priority |
|---|---|---|
| FR-1201 | The system shall aggregate check-in data at the institution level only after a configurable minimum cohort size (e.g. 20+ students) has opted in, to prevent re-identification. | High |
| FR-1202 | The system shall ensure Campus Mode queries return only aggregate statistics and shall never expose row-level student records to a University Admin role. | High |
| FR-1203 | The system shall allow students to opt in or out of contributing to Campus Mode aggregates independently of using the core product. | High |
| FR-1204 | The system shall allow University Admin users to filter aggregate trends by time period (e.g. by week, by term/midterm window). | Low |

**Backend / Logic Notes**
- Aggregation queries run against a separate anonymized read-model (e.g. materialized view) that strips `user_id` and any free-text content before Campus Mode ever queries it.
- Role-based access control (Section 5) strictly separates the University Admin role from any endpoint capable of returning individual-level data.

## 4. External Interface Requirements

### 4.1 User Interfaces

The primary user interface is the responsive web application described per-feature in Section 3. Overall information architecture consists of three persistent destinations (Check-In, Today's RESET, Insights) plus Settings/Privacy and, for University Admin users, a separate Campus Mode dashboard. Navigation is consistent across breakpoints; mobile uses a bottom tab bar, desktop uses a left sidebar.

### 4.2 Hardware Interfaces

Not applicable. RE:SET deliberately avoids any hardware-dependent input (camera, microphone, biometric sensors, wearables) for the v1 scope defined in this document.

### 4.3 Software Interfaces

| Interface | Purpose | Notes |
|---|---|---|
| LLM API (e.g. Anthropic Claude API) | Natural-language generation for pattern summaries, RESET plans, insights, and multi-language copy. | Receives pre-computed statistics/categories only, not raw diagnostic prompts; never used for the underlying trend math. |
| PostgreSQL | Primary relational data store. | See Section 6.1 for entities. |
| LangGraph orchestration runtime | Coordinates the Pattern, Risk/Trend, Personalization, Intervention, Reflection, and Safety agents as a directed pipeline. | Ensures Safety Agent runs before any recommendation-generating agent. |
| Authentication provider | Student/Admin login and session management. | Email/password at minimum for MVP; university SSO integration noted as a future enhancement, not v1. |

### 4.4 Communication Interfaces

- All client-server communication shall occur over HTTPS (TLS 1.2+).
- The backend shall expose a REST API with JSON request/response bodies.
- Real-time RESET-completion timer state is client-local; no WebSocket dependency is required for v1.

## 5. Non-Functional Requirements (NFR)

| NFR-ID | Category | Requirement | Target/Metric |
|---|---|---|---|
| NFR-01 | Performance | Standard API responses (check-in submission, plan retrieval) shall return within a target time. | < 500 ms p95 (excluding AI generation calls) |
| NFR-02 | Performance | AI-generated content (pattern summary, RESET plan) shall complete within an acceptable perceived-wait time. | < 5 s p95, with a loading state shown throughout |
| NFR-03 | Scalability | The system shall support growth from a hackathon demo cohort to a pilot university population without architectural rework. | Up to 5,000 concurrent students in pilot phase |
| NFR-04 | Availability | The core check-in and RESET flow shall remain available with minimal downtime. | 99.5% monthly uptime target (pilot phase) |
| NFR-05 | Reliability & Backup | Wellness data shall be durably stored with regular backups. | Daily automated backups; point-in-time recovery within 24h |
| NFR-06 | Maintainability | Codebase shall separate the agent pipeline, API layer, and data layer to allow independent iteration on AI prompts vs. UI vs. schema. | Modular service boundaries; agent logic isolated from API routing |
| NFR-07 | Usability | A first-time student shall be able to complete a daily check-in without instructions. | Median check-in completion under 30 seconds |
| NFR-08 | Accessibility | All primary flows shall meet baseline accessibility standards. | WCAG 2.1 AA color contrast; full keyboard navigation; screen-reader labels |
| NFR-09 | Portability / Compatibility | The web app shall render correctly across major evergreen browsers and common mobile viewport sizes. | Latest 2 versions of Chrome, Safari, Edge, Firefox; 360px+ width |

### Security Requirements

| Area | Requirement |
|---|---|
| Authentication | Email/password authentication with hashed (e.g. bcrypt/argon2) credential storage; session tokens (e.g. JWT) with reasonable expiry. |
| Authorization | Role-based access control strictly separating Student, University Admin, and System Administrator permissions, enforced server-side on every endpoint (not client-side only). |
| Data Encryption | TLS in transit for all traffic; encryption at rest for the database, particularly for free-text notes and any personally identifiable fields. |
| Password & Session Policy | Minimum password complexity requirements; session timeout after a period of inactivity; ability to revoke active sessions. |
| Input Validation | Server-side validation and parameterized queries on all inputs to prevent SQL injection; output encoding to prevent XSS in any user-generated free-text content that is rendered back to the UI. |
| Audit Logging & Monitoring | Logging of authentication events, Safety Agent activations, and Campus Mode data access, without over-retaining raw sensitive free-text beyond operational need. |
| Rate Limiting | Rate limiting on check-in submission, login attempts, and AI-generation endpoints to prevent abuse and control API cost. |
| Vulnerability Management | Dependency scanning and a defined patching cadence for backend and frontend packages prior to any production/pilot deployment. |

## 6. Other Requirements

### 6.1 Database Requirements

Key entities (high-level; not full DDL):

| Entity | Purpose | Key Relationships |
|---|---|---|
| users | Student, Admin, and System Administrator accounts; auth credentials, role, language preference, Campus Mode opt-in flag. | Parent of daily_checkins, patterns, interventions |
| daily_checkins | Raw daily submissions: mood, stress, sleep, energy, day-tag, optional free-text note. | Belongs to users; source for wellness_signals |
| wellness_signals | Normalized/derived signal values per day per student used for trend computation. | Derived from daily_checkins |
| patterns | Computed trend deltas and Risk/Trend classification per evaluation. | Belongs to users; references contributing wellness_signals |
| interventions | Generated RESET plans, linked to the triggering pattern. | Belongs to users and patterns |
| intervention_results | Completion status and before/after outcome for each intervention. | Belongs to interventions |
| institutions | University/organization records for Campus Mode. | Parent of an anonymized aggregate read-model |

- Data retention: personal check-in and free-text data retained while the account is active, plus a defined grace period after deletion request (e.g. 30 days) to allow recovery before hard deletion.
- Backup & recovery: daily automated backups with point-in-time recovery, per NFR-05.
- Data volume: modest for hackathon/pilot scale (a few thousand students, one check-in/day); no special partitioning required at v1, but schema should allow it later.

### 6.2 Legal and Regulatory Requirements

RE:SET collects sensitive wellness-related data, which warrants careful handling even though this document does not assert formal legal compliance. The following should be treated as guidance requiring dedicated legal review, not a compliance guarantee:

- Applicable local data-protection law in Pakistan (and any jurisdiction the product later expands to) should be reviewed for requirements around consent, data localization, and sensitive personal data handling.
- If the product expands to users in regions covered by GDPR, CCPA, or similar frameworks, additional consent, data-subject-rights, and cross-border-transfer requirements would apply and require separate review.
- A clear Terms of Service and Privacy Policy shall be published and linked from the app before any real (non-demo) user data is collected.
- Because RE:SET touches wellness/mental-health-adjacent data, the team should seek legal guidance on whether any healthcare-adjacent data regulations apply, even though the product explicitly avoids clinical/diagnostic claims.
- Legal/regulatory compliance status is explicitly unresolved at the time of this document and requires review before any pilot beyond the hackathon demo.

### 6.3 Internationalization and Localization

- Initial supported languages: English, Urdu, Roman Urdu (see Section 3.11).
- Right-to-left/script rendering support required for Urdu.
- Dates, times, and numbers formatted per the student's selected locale; no currency formatting is required since the product has no payment flow.
- Static UI copy managed via i18n resource files; AI-generated copy (pattern summaries, RESET plans, insights) generated directly in the target language by instructing the LLM, with periodic human review of translation quality.
